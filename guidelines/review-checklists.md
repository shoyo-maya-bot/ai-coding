# 人のレビュー観点（RP1〜RP5）

各フェーズの区切りで、人がこのチェックリストで確認してから次へ進めます。指摘は課題管理ツールに起票し、
MUST（必須の修正）/ WANT（望ましい修正）/ NITS（軽微）/ Q（質問）の区分を付けます（指摘の分析は quality-analytics）。

## RP1 計画レビュー（フェーズ 1 の後）

- [ ] 設計書の全ての処理手順・入力チェック・メッセージ・テーブル操作が、対応表の要件になっている
- [ ] 要件 1 つが 1〜数個のテストで確かめられる大きさになっている
- [ ] 生成ファイル一覧が [project-structure.md](project-structure.md) と [templates/](templates/) に沿っている
- [ ] 設計書のあいまいな点・矛盾が「確認事項」として挙がっている（推測で埋めていない）
- [ ] 承認したら `spec-trace pin` で設計書のハッシュを記録した

## RP2 コードレビュー（フェーズ 2 の後）

- [ ] 層の責務が守られている（Controller に業務ロジックが無い、Service に HTTP の概念が無い）
- [ ] 例外・メッセージ ID・ログが [coding-standards.md](coding-standards.md) どおり
- [ ] SQL が設計書のテーブル操作どおりで、`#{}` を使っている
- [ ] トランザクション境界が設計書どおり
- [ ] Checkstyle・SpotBugs の除外が追加されていない（あれば理由が妥当）
- [ ] 不要なコード・設計書に無い機能が足されていない

## RP3 テストレビュー（フェーズ 3 の後）

- [ ] 期待値が設計書から決められている（実装の動きをなぞっていない）
- [ ] 正常系・異常系・境界値がそろっている。分岐網羅の不足理由が説明されている
- [ ] 1 テスト 1 観点で、テスト名から確かめている内容が分かる
- [ ] アサーションが弱められていない（`isNotNull()` だけ、などで済ませていない）
- [ ] Karate のシナリオが設計書の API の結果（ステータス・メッセージ ID）を確かめている

## RP4 最終確認（フェーズ 4 の後）

- [ ] reviewer の判定表（N1〜N6）の NG・要確認を全て判断した
- [ ] 対応表の全要件が proven、`spec-trace check --require proven --enforce-drift` が通る
- [ ] 設計書側の誤り・不足が見つかった場合、設計書の修正依頼を起票した

## RP5 PR レビュー（フェーズ 5 の後）

- [ ] CI（D1〜D11）が全て通っている
- [ ] PR 本文にゲート結果・判定表・確認事項の結論が載っている
- [ ] 変更範囲が計画どおり（関係ないファイルの変更が無い）

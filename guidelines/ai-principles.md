# AI 活用の原則

## 位置づけ

AI（GitHub Copilot のエージェント）は、設計書から **β 版** のソースと単体テストを作る道具です。
最終的な品質の担保は人が行います。AI を使っても、成果物の責任の所在は変わりません。

## 品質担保の 5 原則

1. **実行の指示と成果物の格納は人が行う** — どの設計書で、どの工程を回すかは人が決める。AI に自律実行を丸投げしない
2. **AI の生成物（β 版）は全量レビューする** — 生成物をそのまま採用しない。人がレビューして修正事項を洗い出す
3. **AI レビューは補助** — AI によるレビュー（非決定論ゲート）は人のレビューを置き換えない
4. **課題はチケットで追跡する** — レビューで見つけた修正事項は課題管理ツールに起票し、対応漏れを防ぐ
5. **設計書に AI が必要な情報を書く** — パラメータファイル名・メッセージ ID・テーブル名など（[design-doc-requirements.md](design-doc-requirements.md)）

## 手作業の開発との違い

| 観点 | 手作業 | AI 駆動 |
|---|---|---|
| 設計書の形式 | Excel が中心 | Markdown + 図（draw.io）、API は OpenAPI。AI が必要な情報を明記 |
| 実装・単体テスト | 人が書く | AI が β 版を生成（実行の指示は人） |
| 品質担保 | レビューとテスト | 決定論ゲート（機械判定）+ AI レビュー + β 版の全量レビュー |
| 課題管理 | 手で起票 | レビュー結果から起票（ツールで補助） |
| 証跡 | 個別に保存 | 成果物・履歴・レビュー証跡を GitHub で一元管理 |

## 工程ごとの使い方

| 工程 | AI の使い方 | 道具 |
|---|---|---|
| 設計 | Excel の設計書を Markdown・OpenAPI に変換し、AI でドキュメントレビュー | doc-to-markdown、office-review、design-diff |
| 開発〜単体テスト | Markdown の設計書からソースと単体テストの β 版を生成し、対応表で裏付け | このリポジトリ |
| 結合テスト | API テストをシナリオ（Karate）で自動化 | このリポジトリの template |
| リリース・運用 | 障害調査の補助（ログ・設計書を読ませて原因候補を挙げる） | Copilot のエージェント |
| 全工程 | 指摘の傾向分析と改善 | quality-analytics |

## 単体テストコードの使いどころ

| 場面 | 目的 | ポイント |
|---|---|---|
| 初期開発 | 分岐網羅（C1）のテストケースをそろえる | 一度で完成させず、複数回の修正で精度を上げる |
| 小規模な改修 | 影響範囲の担保 | 改修部分に絞ってテストを足し、既存テストでデグレを防ぐ |
| フレームワークのバージョンアップ | 移行時のデグレ検知 | 既存テストをそのまま再利用する |
| 共通 | 網羅性・妥当性の確認 | AI レビューで補助し、最終判断は人 |

## AI 利用の上限

費用とリクエスト数に上限を設け、超えそうなら止めて人が判断します（使った量はラン記録に書く。[eval/](../eval/README.md)）。

| 対象 | 上限 | 超えたとき |
|---|---|---|
| 追加の費用（Copilot のプレミアムリクエストの超過分など、契約の定額を超える課金） | **既定 0 円**（予算を設定しない限り、追加の課金はしない） | AI の利用を止める。続けるなら、費用の承認者が予算を決めてから |
| 1 ラン（1 機能・5 フェーズ）のプレミアムリクエスト | 50 回 | そのランを止めて人に戻す（設計書が大きすぎる・指示がぶれていることが多い。機能を分ける） |
| 1 フェーズの自動修正 | 3 回（[workflow.md](workflow.md) の止まる条件） | 人に戻す |
| 外部の有料 API（LLM の API を直接呼ぶなど） | 使わない（このリポジトリの手順は Copilot の契約の範囲だけで動く） | 使う必要が出たら、費用の承認者と情報の取り扱いの担当に相談する |

- 上限の数は、組織の Copilot の契約・予算に合わせて変えてよい（変えたらこの表を直す PR を出す）
- 1 ランで使ったリクエスト数は Copilot の利用状況（Settings の Usage）で見て、ラン記録の「AI のリクエスト数」に書く

## AI の申告をそのまま信じない

AI は「実装しました」「テストが通りました」と報告しますが、関数が無い・テストが何も確かめていない、ということが起きます。

- 状態（実装済み・テスト済み）は **CI が実在で裏付ける**（spec-trace、[traceability.md](traceability.md)）
- ゲートを通すための **チェックの骨抜きを禁止する**（[workflow.md](workflow.md) の禁止事項）
- 報告には **実行したコマンドと結果** を必ず添えさせる
